# 食序 ORDINE 提前准备设计

**日期：** 2026-08-30

**状态：** 已确认

**适用范围：** 个人菜谱；本规格只包含提前准备模块，不包含周菜单、家庭共享或系统级定时通知

## 1. 目标

用户在决定做一道菜时，能够在菜谱列表和详情页提前看到必须预留的时间，例如牛肉需要腌制 30 分钟、绿豆需要浸泡 4 小时、冷冻食材需要提前一晚解冻。进入正式烹饪步骤前，用户可以逐项确认这些准备已经完成。

从网页、图文、视频文案或截图导入菜谱时，AI 应把来源明确提到的腌制、浸泡、解冻、醒发、静置、回温等事项整理为结构化提前准备草稿，交给用户检查后保存。

核心价值是防止用户开始做饭后才发现食材尚未处理，同时为未来的计划开饭时间和系统提醒保留稳定的数据基础。

## 2. 非目标

- 第一阶段不增加周菜单、日历或计划开饭时间。
- 第一阶段不发送浏览器推送、短信、邮件或系统定时通知；没有计划开饭时间时，无法可靠计算通知时刻。
- 不根据常识擅自生成来源没有提到的腌制或浸泡时间。
- 不提供食品安全、医学、减脂或营养效果保证。
- 不把“切块、切丝、洗净”等即时处理全部迁移为提前准备事项。
- 不记录每一次准备任务的历史完成情况。
- 不改变现有 Next.js、Supabase、Vercel 和 Supabase Auth 技术栈。

## 3. 现有能力与方案选择

现有 `recipe_ingredients.preparation_note` 适合保存“切丝”“洗净”“去皮”等食材级简短备注；`recipe_steps.timer_seconds` 适合正式烹饪过程中的计时。这两类数据都不能准确表达“做饭前 4 小时开始浸泡”。

本模块采用独立的 `recipe_preparations` 表，并将其作为菜谱的一级子资源。相比给食材备注增加一个时间字段，独立资源可以表达不关联单一食材的任务；相比给普通步骤增加 `phase` 字段，它不会污染现有的烹饪步骤顺序、步骤计时器和伴做流程。

每个提前准备事项可以关联一个菜谱食材，也可以不关联食材。精确时间使用分钟存储，来源只有“提前一晚”“泡至变软”等描述时保留原始文字。

## 4. 用户体验

### 4.1 菜谱列表

- 存在提前准备事项时，菜谱卡显示最长提前时间，例如“需提前 4 小时准备”。
- 只有非精确时间时，显示“有提前准备事项”。
- 没有提前准备事项的菜谱卡保持当前样式。
- 列表只显示摘要，不展开全部事项。

### 4.2 菜谱详情

- 在基础信息之后、食材之前显示独立的“提前准备”卡片。
- 按 `leadTimeMinutes` 从大到小排列；非精确时间排在精确时间之后，再按用户排序排列。
- 每项展示时间标签、关联食材名称和准备说明。
- 精确时间使用最易读的单位展示：小于 60 分钟显示分钟，整小时显示小时，整天显示天，其余显示组合时间。
- 原始时间文字直接显示，例如“提前一晚”或“泡至变软”。

示例：

```text
提前准备
提前 4 小时  绿豆：加足量清水浸泡
提前 30 分钟 牛肉：加入生抽和淀粉抓匀腌制
开始前        葱姜蒜：切好备用
```

### 4.3 菜谱编辑器

在食材与烹饪步骤之间新增“提前准备”区块：

- 可以添加、删除和调整顺序。
- 可以从当前菜谱食材中选择一个关联食材，也可以选择“不关联食材”。
- 必填“准备说明”。
- 时间输入由数值和单位组成，单位支持分钟、小时、天；保存时统一换算为分钟。
- 可以改用“文字时间”，保存“提前一晚”“泡至变软”等无法精确换算的描述。
- 精确时间和文字时间至少填写一个；两者同时存在时优先展示原始文字，并保留精确分钟用于排序和未来提醒。
- 删除食材时，对应提前准备事项不自动删除，而是解除关联并保留说明，防止用户内容意外丢失。

### 4.4 开始烹饪

- 菜谱存在提前准备事项时，点击“开始烹饪”先进入准备确认页。
- 用户逐项勾选完成后进入现有第一步烹饪页面。
- 用户可以选择“仍然开始烹饪”，但页面应明确显示尚未完成的事项。
- 勾选状态仅保存在当前设备的本次烹饪会话中；完成或重置烹饪后清空。
- 提前准备事项不启动现有步骤计时器。

## 5. 数据库设计

新增表 `public.recipe_preparations`：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | `uuid` | 主键，由客户端生成，便于编辑草稿和原子保存 |
| `user_id` | `uuid` | 必填，关联 `auth.users` |
| `recipe_id` | `uuid` | 必填，关联当前用户的菜谱 |
| `recipe_ingredient_id` | `uuid` | 可空，必须属于同一用户和同一菜谱 |
| `instruction` | `text` | 必填，去空格后 1–500 字符 |
| `lead_time_minutes` | `integer` | 可空，范围 1–43200，即最多提前 30 天 |
| `timing_text` | `text` | 可空，去空格后最多 60 字符 |
| `sort_order` | `integer` | 必填且不小于 0，同一菜谱内唯一 |
| `created_at` | `timestamptz` | 默认当前时间 |
| `updated_at` | `timestamptz` | 默认当前时间并复用更新时间触发器 |

约束：

- `lead_time_minutes` 与 `timing_text` 至少一个非空。
- `(user_id, id)` 和 `(user_id, recipe_id, id)` 建立唯一约束，以支持所有权复合外键。
- `(recipe_id, sort_order)` 唯一。
- `(user_id, recipe_id)` 建立读取索引。
- 菜谱删除时级联删除提前准备事项。
- 食材删除时使用复合外键 `ON DELETE SET NULL (recipe_ingredient_id)`，保留用户写下的准备说明。
- 启用并强制 RLS；读取、写入、更新和删除均要求 `auth.uid() = user_id`。

不得把提前准备事项直接存成 `recipes` 表中的 JSON 数组。独立表更适合约束所有权、关联食材、排序和未来查询提醒。

## 6. 应用数据结构

菜谱保存结构新增：

```ts
type RecipePreparationInput = {
  preparationId: string;
  recipeIngredientId: string | null;
  instruction: string;
  leadTimeMinutes: number | null;
  timingText: string | null;
  sortOrder: number;
};
```

`RecipeSaveInput`、`RecipeDetail` 和离线 `RecipeSnapshot` 增加 `preparations` 数组。所有入口使用同一个 Zod 结构验证，避免手动新建、AI 导入和编辑旧菜谱出现不同规则。

菜谱列表查询增加准备摘要：

```ts
type RecipePreparationSummary = {
  count: number;
  maxLeadTimeMinutes: number | null;
};
```

列表查询只返回数量和最长提前分钟数，不载入所有准备说明。

## 7. 保存与读取流程

现有 `save_recipe(jsonb)` 继续作为菜谱的唯一原子保存入口：

1. 校验当前登录用户和完整 `RecipeSaveInput`。
2. 保存菜谱基础信息、分类和标签。
3. 重建食材、提前准备、步骤和步骤食材关联。
4. 提前准备在食材保存后、步骤保存前写入，确保可选食材外键已经存在。
5. 任意一项失败时整次事务回滚，不产生半份菜谱。

读取菜谱详情时，提前准备与分类、标签、食材、步骤并行查询，再按排序规则组合为 `RecipeDetail`。旧菜谱没有准备数据时返回空数组，页面不显示空卡片。

## 8. AI 导入

`RecipeImportDraft` 新增：

```ts
type RecipePreparationDraft = {
  ingredientName: string | null;
  instruction: string;
  leadTimeMinutes: number | null;
  timingText: string | null;
};
```

AI 提取规则：

- 只提取来源明确表达的腌制、浸泡、解冻、醒发、静置、回温或其他提前任务。
- “30 分钟”“4 小时”“2 天”换算为分钟。
- “提前一晚”“泡至变软”等放入 `timingText`；能同时合理换算时仍保留原文。
- 来源只说“提前泡好”但没有时间时，保留说明并添加需要用户确认的警告。
- 不使用模型常识补写来源没有出现的时间。
- `ingredientName` 通过现有的标准化名称规则映射到菜谱食材；映射失败时保留未关联事项，不丢弃。
- AI 结果仍然只进入编辑草稿，用户检查并保存后才写入正式菜谱。

现有 `preparationNote` 继续保存“切片、切块、洗净、去皮”等即时食材处理。若来源表达“牛肉切片后腌制 30 分钟”，食材备注保存“切片”，提前准备事项保存“加入调料腌制”和 30 分钟。

## 9. 离线与烹饪会话

- 离线菜谱快照包含完整 `preparations` 数组。
- 离线详情页展示提前准备卡。
- 当前烹饪会话增加已完成准备事项 ID 集合。
- 会话状态只存本地，不回写数据库，不与其他设备同步。
- 当前步骤计时器逻辑保持不变。

## 10. 错误处理与安全

- 所有客户端输入通过 Zod 校验，数据库再次通过约束和 RLS 防护。
- 用户不能关联其他菜谱或其他用户的食材。
- AI 返回无效时间、超长文本或不存在的食材时，不直接写数据库；进入警告或未关联状态供用户修改。
- 保存失败时保留编辑器内容，并显示可操作的错误信息。
- 数据库迁移只新增表、索引、策略和保存函数变更，不修改或删除已有菜谱数据。
- 正式 Supabase 项目执行迁移前必须单独确认项目身份、迁移内容和执行权限。

## 11. 测试与验收标准

### 11.1 自动测试

- Zod：精确时间、文字时间、缺失时间、时间范围和食材关联校验。
- 数据库：RLS、跨用户隔离、跨菜谱食材拒绝、食材删除后解除关联、菜谱删除级联。
- 保存函数：新增、编辑、删除准备事项以及事务失败回滚。
- AI：识别“腌制 30 分钟”“浸泡 4 小时”“提前一晚”，不为空白来源编造时间。
- 映射：关联食材成功和映射失败保留事项。
- 编辑器：添加、排序、删除、分钟/小时/天换算和文字时间编辑。
- 列表与详情：最长提前时间摘要和排序展示。
- 烹饪：准备确认、仍然开始、完成后清理会话。
- 离线：快照读写和离线展示。
- 全量执行 TypeScript、ESLint、相关 Vitest 和 Production build。

### 11.2 人工验收

1. 手动创建含“牛肉腌制 30 分钟”和“绿豆浸泡 4 小时”的菜谱。
2. 确认列表显示“需提前 4 小时准备”。
3. 确认详情按 4 小时、30 分钟顺序展示。
4. 编辑并保存后重新打开，内容和食材关联不丢失。
5. 用包含上述描述的文字或网页导入，确认 AI 草稿正确生成准备事项。
6. 删除被关联食材，确认准备说明保留且变为未关联。
7. 点击开始烹饪，确认先看到准备清单并可以继续进入步骤。
8. 离线打开最近菜谱，确认提前准备卡仍可查看。
9. 验证现有菜谱、购物清单、步骤计时和导入流程没有回归。

## 12. 交付顺序

本阶段只实现一个可独立验收模块：

1. 数据库与保存结构。
2. 手动编辑、列表摘要和详情展示。
3. AI 导入映射。
4. 烹饪前确认和离线快照。
5. 全量测试、提交并推送当前功能分支，等待验收。

本模块验收完成后，再独立实现已经确认的“AI 智能分类与标签”，不把两个模块混在同一次提交中。

## 13. 后续扩展

当产品增加“计划开饭时间”或周菜单后，可以基于 `lead_time_minutes` 计算真实提醒时刻：

```text
提醒时刻 = 计划开始烹饪时间 - 提前分钟数
```

届时再增加通知授权、提醒计划和跨设备同步，不需要改变本模块的准备事项数据模型。
