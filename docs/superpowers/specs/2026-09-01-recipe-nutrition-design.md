# 食序 ORDINE 营养与饮食目标设计

**日期：** 2026-09-01

**状态：** 实施方案待确认

**适用范围：** 模块 12；个人菜谱、AI 来源导入、菜谱列表与离线菜谱

## 1. 目标

用户可以为菜谱记录每份热量、蛋白质、脂肪和碳水，并在菜谱编辑、详情、列表和离线详情中看到这些数据。数值可以留空、单独填写或修改，不要求四项同时存在。

通过 AI 来源导入得到的营养数值必须醒目标记为“估算”，并进入现有 AI 审核流程；信息不足时保持为空，不允许为了填满表单而编造。模块不提供医疗判断、减重承诺或个性化营养处方。

“减脂”“增肌”“高蛋白”继续使用现有用户标签体系。模块提供更方便的饮食目标快捷标签和筛选，但不会新增第二套分类表，也不会根据某个固定阈值自动把菜谱判定为减脂或增肌。

## 2. 已确定的默认与边界

- 所有营养值均按“每份”保存；基础份数继续使用现有 `recipes.base_servings`。
- 热量单位固定为千卡（kcal），蛋白质、脂肪和碳水单位固定为克（g）。
- 营养项全部可空；至少填写一项时才保存营养记录，四项都为空时删除对应记录。
- `is_estimated` 默认勾选。只有用户明确掌握包装标签或可靠来源数据时，才建议取消“估算”标记。
- AI 导入只在食材用量和基础份数足以支撑估算时返回数值；否则返回空值和警告。
- AI 导入产生任何营养数值时，`is_estimated` 必须为 `true`，用户确认后才能保存。
- 不接入付费营养数据库、第三方健康平台或新的 AI 服务商。
- Qwen 3.8 Flash 继续作为默认模型；现有模型路由保持不变。
- 不增加每日热量目标、体重管理、饮食打卡、健康评分、过敏风险或疾病建议。
- 第一版不按热量区间、宏量比例或营养阈值进行数据库筛选，只提供已有饮食目标标签筛选。
- 当前模块仍只服务个人用户，不增加家庭共享。

## 3. 方案比较与选择

### 3.1 采用方案：一对一营养表 + 复用标签

新增 `recipe_nutrition` 一对一表保存每份营养值和估算标记；饮食目标继续复用 `tags` 与 `recipe_tags`。

优点：

- 营养字段不会继续扩大核心 `recipes` 表。
- 删除菜谱时营养数据自动级联删除，所有权可通过复合外键和 RLS 固化。
- 以后增加膳食纤维、钠等字段时，只扩展营养资源，不影响菜谱主表。
- “减脂”“增肌”“高蛋白”仍能使用现有搜索、标签创建和筛选能力，不产生重复数据。

### 3.2 未采用：直接给 `recipes` 增加四个字段

实现最少，但会把可选且未来可能扩展的营养属性放入每一行菜谱，估算状态也会继续扩大主表。当前已有多个子资源，独立一对一表更符合现有结构。

### 3.3 未采用：食材营养数据库和自动精确计算

这种方案需要可靠的食材标准化、品牌差异、烹饪损耗和营养数据源，免费条件下无法保证准确性，也会显著扩大工程量。本模块只做可编辑估算，不做营养数据库。

## 4. 用户体验

### 4.1 菜谱编辑

在基础信息后新增“每份营养”卡片，包含：

- 热量（千卡）
- 蛋白质（克）
- 脂肪（克）
- 碳水（克）
- “这些数值是估算值”复选框

四个输入均允许空值和小数，输入 0 是合法值。四项全部为空时不保存营养记录；存在任一数值时，复选框默认勾选。

卡片底部固定显示：“营养数据仅供日常记录，不构成医疗或专业营养建议。”

同一区域增加“饮食目标”快捷标签：减脂、增肌、高蛋白。已经存在的标签直接切换选中状态；尚不存在的标签显示“创建并选择”，点击后复用现有标签创建动作。普通自定义标签仍保留原位置和行为。

### 4.2 菜谱详情

存在任一营养值时，在提前准备与食材清单之间显示“每份营养”卡片：

- 只显示有值的项目，不用 `0` 代替缺失。
- 估算数据显示“估算”徽标和免责声明。
- 数值统一最多保留一位小数；整数不显示无意义的小数位。
- 不计算或展示“健康”“低卡”“适合减脂”等结论。

### 4.3 菜谱列表与筛选

- 菜谱卡片存在营养数据时，最多展示“约 N 千卡”和“蛋白质 N g”两项，避免卡片过载。
- “估算”数值使用“约”作为前缀；非估算数据不加“约”。
- 搜索区增加饮食目标快捷筛选，只映射当前用户已有的“减脂”“增肌”“高蛋白”标签。
- 快捷筛选和现有标签下拉共用 `tag` 查询参数，不增加新的 URL 状态或数据库筛选接口。

### 4.4 AI 来源导入

AI 草稿新增可空的 `nutrition`：

```ts
type RecipeNutritionDraft = {
  caloriesKcal: number | null;
  proteinGrams: number | null;
  fatGrams: number | null;
  carbsGrams: number | null;
} | null;
```

模型提示规则：

- 返回每份数值，不返回整份菜谱总量。
- 只有食材用量和基础份数足以支持估算时才填写。
- 无法可靠估算的项目保持 `null`，并添加中文 warning。
- 不输出减重、增肌效果或医学建议。
- `fieldChecks` 为四个营养路径分别返回 `explicit`、`inferred` 或 `missing`。

应用层规则：

- AI 提供的营养数值允许以 `inferred` 形式保留在草稿中，不像关键火候和计时那样清空。
- `missing` 对应值必须清空。
- 只要保留任一 AI 营养值，映射到编辑器时强制 `isEstimated: true`。
- 任一营养字段为 `inferred` 或 `missing` 时，沿用现有“我已检查以上 AI 推断和缺失内容”确认门禁。
- 旧导入任务没有 `nutrition` 时按 `null` 解析，不能因为 schema 升级失效。

### 4.5 离线菜谱

营养值属于菜谱详情的一部分，随现有离线快照保存。离线详情使用与在线详情相同的只读营养卡片。快照 `dataVersion` 从 2 升到 3；旧版本继续按当前策略视为不兼容并重新缓存，不进行复杂迁移。

## 5. 数据库设计

### 5.1 `public.recipe_nutrition`

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `recipe_id` | `uuid` | 必填；与 `user_id` 组成复合主键并关联当前用户菜谱，删除菜谱时级联删除 |
| `user_id` | `uuid` | 必填，关联 `auth.users`；与 `recipe_id` 组成复合主键 |
| `calories_kcal` | `numeric(8,2)` | 可空，0–100000 |
| `protein_grams` | `numeric(8,2)` | 可空，0–10000 |
| `fat_grams` | `numeric(8,2)` | 可空，0–10000 |
| `carbs_grams` | `numeric(8,2)` | 可空，0–10000 |
| `is_estimated` | `boolean` | 必填，默认 `true` |
| `created_at` | `timestamptz` | 默认当前时间 |
| `updated_at` | `timestamptz` | 默认当前时间并复用更新时间触发器 |

约束：

- `(user_id, recipe_id)` 为主键，同时提供 owner-first 查询索引，不再创建重复索引。
- 四个数值均允许 0，但不能为负数或超过上限。
- 必须至少存在一个非空营养值；空营养记录不应写入数据库。
- `(user_id, recipe_id)` 建立读取索引；主键已经覆盖按 `recipe_id` 查询。

### 5.2 RLS 与权限

`recipe_nutrition`：

- 启用并强制 RLS。
- 撤销 `public`、`anon`、`authenticated` 的默认权限，再只向 `authenticated` 显式授予所需 CRUD。
- 分别创建 SELECT、INSERT、UPDATE、DELETE 策略。
- 所有策略要求 `(select auth.uid()) = user_id`。
- UPDATE 同时使用 `USING` 与 `WITH CHECK`，不能改变记录所有者。
- 不使用 `SECURITY DEFINER`。

这也兼容 Supabase 2026 年对新表 Data API 暴露方式的收紧：新表必须明确配置 grants，RLS 与 grants 不能互相替代。

### 5.3 原子保存

更新现有 `public.save_recipe(p_payload jsonb)`，在同一事务中：

1. 保存菜谱、标签、食材、步骤和提前准备。
2. `nutrition` 存在且至少一项有值时，按 `(recipe_id)` upsert `recipe_nutrition`。
3. `nutrition` 为空或四项全空时，删除当前用户该菜谱的营养记录。
4. 任何营养约束或所有权校验失败时，整个菜谱保存回滚。

不新增第二个保存 Server Action，避免菜谱成功但营养保存失败的部分状态。

## 6. 应用类型与接口

新增 `src/features/nutrition/`：

- `constants.ts`：单位、固定饮食目标标签名称和展示配置。
- `schemas.ts`：营养输入、空值归一化和范围校验。
- `types.ts`：`RecipeNutrition` 与表单类型。
- `format.ts`：数值与“约”前缀格式化。
- `components/recipe-nutrition-editor.tsx`：可编辑营养表单。
- `components/recipe-nutrition-card.tsx`：在线与离线共用的只读卡片。
- `components/diet-goal-tags.tsx`：编辑器快捷标签。
- `components/diet-goal-filters.tsx`：列表快捷筛选。

现有接口扩展：

```ts
type RecipeNutrition = {
  caloriesKcal: number | null;
  proteinGrams: number | null;
  fatGrams: number | null;
  carbsGrams: number | null;
  isEstimated: boolean;
};

type RecipeSaveInput = {
  // existing fields
  nutrition: RecipeNutrition | null;
};

type RecipeSummary = {
  // existing fields
  nutrition: RecipeNutrition | null;
};
```

菜谱详情查询额外读取一行 `recipe_nutrition`。菜谱列表通过现有 `search_recipe_summaries` 返回营养 JSON；函数参数保持不变，因为饮食目标筛选继续复用 `p_tag_id`。PostgreSQL 不能通过 `CREATE OR REPLACE FUNCTION` 改变表返回类型，因此 migration 需要在同一事务中撤销旧函数权限、删除旧签名并以原参数重新创建，再恢复 `authenticated` 执行权。旧调用参数保持兼容，新增返回字段不会要求调用端提供新参数。

## 7. 错误处理与兼容性

- 表单非法数值在客户端显示具体字段错误，Server Action 使用同一 Zod schema 再次验证。
- 数据库查询营养失败时，菜谱详情整体显示现有加载错误，不静默伪装为“没有营养数据”。
- AI 返回负数、过大值、字符串或结构错误时，整个模型输出按现有安全流程判为无效，不直接保存。
- AI 营养信息不足时允许菜谱继续导入，只显示 warning 和空营养卡片。
- 普通新建、编辑和旧菜谱默认 `nutrition: null`，现有数据不需要回填。
- 旧离线快照版本不读取营养数据，重新在线打开菜谱后生成新版快照。

## 8. 无障碍与响应式

- 营养输入使用可见 label，并在 label 中写明单位。
- 估算复选框提供完整说明和 `aria-describedby`。
- 营养卡片使用定义列表语义，不能只依赖颜色表达“估算”。
- 饮食目标快捷标签使用原生按钮或复选框语义，选中状态提供 `aria-pressed` 或 `checked`。
- 手机端四项营养值使用 2 列网格，桌面端使用 4 列；360px 宽度不横向滚动。
- 加载、空值和错误状态沿用现有卡片样式；没有营养数据时详情页不显示空卡片。

## 9. 测试策略

### 9.1 数据库

- PGlite 验证表结构、约束、索引、强制 RLS、grants 和策略。
- Owner 可以 CRUD；另一用户无法读写；anon 无权限。
- 跨用户 recipe 关联失败。
- 四项全空、负数和超过上限失败；0 与部分字段合法。
- `save_recipe` 在营养 upsert 或删除时保持事务原子性。

### 9.2 应用层

- Zod 覆盖空值、0、小数、上限和全空归一化。
- 查询映射覆盖 numeric 字符串到 number、缺失行和估算标记。
- 编辑器覆盖创建、编辑、清空营养、AI 估算标记和快捷标签。
- 详情、卡片、筛选覆盖部分值、估算文案、缺失隐藏和移动端语义。
- AI schema、提示、Qwen/Gemini 共同契约、审核路径和旧草稿兼容全部有回归测试。
- 离线快照版本、缓存兼容性和离线详情显示有回归测试。

## 10. 人工验收场景

1. 新建菜谱只填写 320 千卡和 28 克蛋白质，保存后详情和列表只显示这两项。
2. 输入 0 克脂肪可以保存；输入负数或超大值时在保存前显示错误。
3. 编辑菜谱清空四项营养值，保存后营养记录被删除，详情不再显示营养卡片。
4. 勾选估算时详情显示“估算”和免责声明；取消勾选后不再使用“约”前缀。
5. 点击“高蛋白”快捷标签，已存在时直接选中，不存在时明确创建并选中；普通标签不受影响。
6. 使用“减脂”快捷筛选后，结果与标签下拉选择同一标签完全一致，分页链接保留筛选。
7. 导入用量明确的菜谱，AI 营养值保留、标记估算并要求审核确认。
8. 导入食材用量不足的菜谱，营养值保持为空并显示“无法可靠估算”的 warning，菜谱仍可保存。
9. 另一个用户无法读取或修改当前用户的营养记录。
10. 缓存菜谱后断网，离线详情仍能看到营养卡片；旧快照不会导致页面崩溃。
