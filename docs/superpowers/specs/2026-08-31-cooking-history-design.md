# 食序 ORDINE 烹饪历史与个人改进设计

**日期：** 2026-08-31

**状态：** 已确认，待实现

**适用范围：** 个人菜谱、引导烹饪和周菜单；本规格只包含模块 9，不包含菜谱版本树、家庭共享或营养分析

## 1. 目标

用户完成一次引导烹饪后，可以留下可选评分、成品照片和“下次注意”备注。记录需要同时保存实际份数与开始、完成时间，并在从周菜单进入烹饪时自动关联对应菜单项。

菜谱详情展示累计烹饪次数、平均评分、最近记录和最近一次“下次注意”，帮助用户把一次次实际经验沉淀到同一道菜上。

本模块只把“已完成的一次烹饪”持久化到 Supabase。当前步骤、计时器和准备勾选仍沿用现有浏览器本地会话，不把烹饪中的高频状态同步到云端。

## 2. 非目标

- 第一版不建立菜谱版本树，不保存每次烹饪时的完整食材与步骤快照。
- 第一版不增加全局烹饪历史中心，只在菜谱详情展示最近记录和统计。
- 第一版不提供记录编辑、批量删除、照片批量管理或社交分享。
- 不记录每一步的点击时间、计时器操作日志或准备事项的逐项完成历史。
- 不增加离线写入队列；离线时可以继续现有引导烹饪，但云端记录需要恢复网络后才能保存。
- 不增加新的图片服务、数据库服务或付费依赖。
- 不改变 Next.js、Supabase、Supabase Auth 和 Vercel 技术栈。

## 3. 方案选择

本模块采用两张规范化表：`cooking_records` 保存一次完整烹饪，`cooking_record_photos` 保存零至三张成品照片。

未采用把照片路径直接存入 JSON 数组的方案，因为独立照片行更容易约束数量、排序、所有权和删除生命周期。未采用完整菜谱快照方案，因为当前需求只需要保留菜名和多次实践反馈，完整版本化会扩大保存、查询和迁移复杂度。

成品照片复用现有私有 `recipe-media` Storage bucket。当前 bucket 已按路径第一段的用户 ID 实施所有权策略，可以在不新增 bucket 和额外配置的前提下安全扩展 `cooking-records` 路径。

## 4. 用户体验

### 4.1 从菜谱开始烹饪

- 现有菜谱详情的“开始烹饪”入口保持不变。
- 进入引导烹饪时继续创建或恢复本地 `CookingSessionV1`。
- 最后一步的“完成烹饪”不再立即清除会话，而是打开复盘面板。
- 直接从菜谱进入时，生成的记录不关联周菜单项。

### 4.2 从周菜单开始烹饪

- 状态为“计划中”的周菜单项增加“开始烹饪”入口。
- 入口传递 `mealPlanEntryId` 和该菜单项的目标份数。
- 烹饪页面在服务端验证菜单项属于当前用户、菜谱一致且未失效；验证失败时忽略关联并给出提示，不能凭查询参数关联他人的菜单项。
- 完成并保存烹饪记录后，同一数据库事务把关联菜单项标记为 `completed`。

### 4.3 完成复盘面板

复盘面板在手机上使用底部友好的对话框布局，在桌面上保持居中，包含：

- 实际份数：必填，默认采用本次引导烹饪的目标份数，可修改。
- 评分：可选，1–5 星。
- 成品照片：可选，最多 3 张，支持拍照或从设备选择。
- 下次注意：可选，最多 2000 字，例如“下次少放盐”“牛肉再薄一点”。

用户不填写评分、照片和备注也可以保存记录。主操作文案为“保存并完成”，次操作为“返回继续烹饪”。当网络或保存出现问题时，显示“重试保存”和“本次不保存记录并退出”；只有用户明确选择不保存时才允许跳过云端记录。

### 4.4 菜谱详情

菜谱详情新增“烹饪记录”区块：

- 显示总烹饪次数。
- 仅基于非空评分计算平均评分，保留一位小数；没有评分时不显示平均分。
- 显示最近 3 次记录，包括完成日期、实际份数、评分、备注和成品照片。
- “下次注意”展示最近一条非空改进备注。
- 没有记录时显示“完成一次引导烹饪后，这里会留下你的经验”。

第一版不增加分页和独立历史页。数据库与查询接口保留以后增加完整历史页的扩展空间。

## 5. 数据库设计

### 5.1 `public.cooking_records`

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | `uuid` | 主键，由客户端预生成，便于在上传照片前确定私有路径 |
| `user_id` | `uuid` | 必填，关联 `auth.users` |
| `recipe_id` | `uuid` | 可空，关联当前用户菜谱；菜谱永久删除时仅将此字段置空 |
| `recipe_title_snapshot` | `text` | 必填，1–120 字；保留完成烹饪时的菜名 |
| `meal_plan_entry_id` | `uuid` | 可空，关联当前用户周菜单项；菜单项删除时置空 |
| `started_at` | `timestamptz` | 必填，来自当前本地烹饪会话开始时间 |
| `completed_at` | `timestamptz` | 必填，由数据库使用当前时间写入 |
| `actual_servings` | `numeric(6,2)` | 必填，范围 0.25–1000 |
| `rating` | `smallint` | 可空，范围 1–5 |
| `improvement_notes` | `text` | 可空，去空格后最多 2000 字 |
| `created_at` | `timestamptz` | 默认当前时间 |
| `updated_at` | `timestamptz` | 默认当前时间并复用更新时间触发器 |

约束与索引：

- `completed_at >= started_at`。
- `(user_id, id)` 唯一，供照片表所有权复合外键使用。
- `(user_id, recipe_id, completed_at desc)` 索引支持菜谱详情最近记录。
- `(user_id, meal_plan_entry_id)` 索引支持菜单关联查询。
- `(user_id, recipe_id)` 复合外键确保只能关联自己的菜谱，删除时只将 `recipe_id` 置空并保留 `user_id`。
- `(user_id, meal_plan_entry_id)` 复合外键确保只能关联自己的菜单项，删除时只将 `meal_plan_entry_id` 置空。

`recipe_title_snapshot` 是有意保留的最小历史快照。菜谱目前通常使用软删除；即使未来发生永久删除，历史记录仍能说明用户做过什么菜。

### 5.2 `public.cooking_record_photos`

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | `uuid` | 主键，由客户端生成 |
| `user_id` | `uuid` | 必填，关联 `auth.users` |
| `cooking_record_id` | `uuid` | 必填，必须属于同一用户 |
| `storage_path` | `text` | 必填，1–500 字，指向私有 `recipe-media` bucket |
| `sort_order` | `smallint` | 必填，只允许 0、1、2 |
| `created_at` | `timestamptz` | 默认当前时间 |

约束与索引：

- `(cooking_record_id, sort_order)` 唯一。
- `(user_id, cooking_record_id)` 建立读取索引。
- `(user_id, cooking_record_id)` 复合外键关联 `cooking_records`，记录删除时级联删除照片元数据。
- `sort_order` 限定为 0–2，配合唯一约束从数据库层保证每条记录最多 3 张照片。

## 6. 数据权限与数据库函数

两张表均：

- 启用并强制 RLS。
- 撤销 `public` 和 `anon` 权限。
- 为 `authenticated` 显式授予所需 CRUD 权限。
- 分别建立 `select`、`insert`、`update`、`delete` 策略，所有策略都要求 `(select auth.uid()) = user_id`。
- `update` 同时使用 `USING` 和 `WITH CHECK`，防止记录被转移给其他用户。

新增 `public.complete_cooking_record(p_payload jsonb)`，使用 `SECURITY INVOKER`：

1. 获取并验证 `auth.uid()`。
2. 验证菜谱存在、属于当前用户且未进入回收站。
3. 可选验证周菜单项属于当前用户，而且菜单项的 `recipe_id` 与本次菜谱一致。
4. 插入烹饪记录和零至三条照片元数据。
5. 存在合法菜单关联时，将菜单项状态更新为 `completed`。
6. 任一步失败则整次数据库事务回滚。
7. 返回 `cooking_record_id`。

函数默认执行权限从 `public` 和 `anon` 撤销，只授予 `authenticated`。不使用 `SECURITY DEFINER` 绕过 RLS。

新增只读 `public.get_recipe_cooking_history_stats(p_recipe_id uuid)`，同样使用 `SECURITY INVOKER`，只统计当前用户的记录并返回：

- `total_count`
- `rated_count`
- `average_rating`
- `latest_improvement_notes`

最近三次记录及其照片仍通过普通表查询读取，并由 RLS 保护。

## 7. 照片存储

照片路径固定为：

```text
{userId}/cooking-records/{cookingRecordId}/{photoId}.webp
```

上传继续复用现有规则：

- 原图只接受 JPG、PNG、WebP，最大 15MB。
- 客户端压缩为 WebP，目标不超过 2MB，最长边 1600px。
- 压缩后绝对上限 5MB。
- `upsert: false`，每张照片使用新的 UUID，避免覆盖和缓存不一致。
- 私有地址只通过短期签名 URL 展示。

保存顺序为：先生成记录 UUID并上传选中的照片，再调用原子完成函数写入记录、照片元数据和菜单状态。数据库保存失败时，对本次已上传路径执行尽力清理；清理失败只记录安全日志，不向用户暴露路径或内部错误。

照片是可选内容。单张照片压缩或上传失败时，复盘面板保留填写内容，允许重试、移除失败照片，或不带照片完成。

## 8. 应用边界与接口

新增功能目录 `src/features/cooking-history/`，避免继续扩大现有 `cooking-screen.tsx`：

- `types.ts`：记录、照片、统计和操作结果类型。
- `schemas.ts`：完成复盘输入的 Zod 校验。
- `actions.ts`：认证、照片元数据提交、完成 RPC 和页面刷新。
- `queries.ts`：统计、最近记录和签名图片地址。
- `media.ts`：成品照片路径、压缩、上传与失败清理。
- `components/cooking-reflection-dialog.tsx`：复盘表单与错误恢复。
- `components/cooking-history-section.tsx`：菜谱详情统计和最近记录。

完成输入固定为：

```ts
type CompleteCookingRecordInput = {
  cookingRecordId: string;
  recipeId: string;
  mealPlanEntryId: string | null;
  startedAt: string;
  actualServings: number;
  rating: number | null;
  improvementNotes: string | null;
  photos: Array<{
    photoId: string;
    storagePath: string;
    sortOrder: number;
  }>;
};
```

现有 `CookingScreen` 只负责控制何时打开复盘面板，并在保存成功或用户明确跳过后调用 `cooking.complete()` 清理会话。表单、上传和云端保存逻辑不放入现有 hook，避免把本地烹饪状态与远程记录写入耦合在一起。

烹饪路由新增可选 `mealPlanEntryId` 查询参数。服务端加载页面时验证关联并把规范化后的 ID 传给 `CookingScreen`；客户端不能自行决定记录归属。

## 9. 数据流

### 9.1 保存成功

```text
最后一步
→ 打开复盘面板
→ 校验份数、评分、备注和照片数量
→ 生成记录/照片 UUID
→ 压缩并上传选中照片
→ complete_cooking_record 原子写记录并完成菜单项
→ 清除本地烹饪会话和计时器
→ 跳转菜谱详情并显示成功提示
→ 详情查询统计、最近记录和签名照片
```

### 9.2 保存失败

```text
上传失败
→ 保留表单与本地烹饪会话
→ 重试、移除照片或不带照片保存

数据库失败
→ 尽力删除本次新上传照片
→ 保留表单与本地烹饪会话
→ 显示可操作的重试提示
```

服务端日志只记录错误阶段、Supabase 错误码和不可识别的请求 ID，不记录照片内容、备注正文、密钥或完整用户输入。

## 10. 删除与历史一致性

- 菜谱软删除不会修改历史记录。
- 菜谱永久删除时，数据库把 `recipe_id` 置空，保留菜名快照和历史内容。
- 周菜单项删除时，把 `meal_plan_entry_id` 置空，历史仍然保留。
- 删除一条烹饪记录时，照片元数据级联删除；Storage 对象需要由未来的记录管理操作显式清理。
- 第一版没有删除记录 UI，因此不会新增未要求的管理入口；数据库关系仍按安全删除设计。
- 删除或修改烹饪记录不会反向把菜单状态改回 `planned`，避免历史维护意外改变周计划。

## 11. 离线与恢复

- 现有引导烹饪仍可依赖本地会话离线运行。
- 离线时打开复盘面板，填写内容保留在组件状态中，但第一版不持久化照片和复盘草稿。
- 保存失败不会自动清理本地烹饪会话。
- 用户恢复网络后可在仍打开的页面重试。
- 用户明确选择“不保存记录并退出”后才清理本地会话。
- 不增加后台同步、Service Worker 队列或冲突解决逻辑。

## 12. 错误处理与可访问性

- 所有客户端输入先经过 Zod 校验，数据库再次通过约束、复合外键、RLS 和原子函数验证。
- 非法 `mealPlanEntryId` 不产生关联，也不能更新任何菜单项。
- 重复提交同一个 `cookingRecordId` 不得生成两条记录；UI 保存期间禁用重复点击。
- 对话框包含明确标题、字段标签、错误摘要和键盘焦点管理。
- 星级评分可用键盘操作，并提供可读的“1 星”至“5 星”标签。
- 图片预览包含删除按钮和替代文本；失败状态不只依赖颜色表达。
- 加载、空状态、保存中、上传失败和数据库失败都有独立文案。

## 13. 测试与验收标准

### 13.1 数据库与安全

- 迁移在 PGlite 中可执行，表、约束、索引、触发器和函数签名正确。
- 匿名用户没有表和函数权限。
- 用户可以读写自己的记录，无法读取、插入、修改或删除其他用户的记录和照片元数据。
- 不能关联其他用户或其他菜谱的周菜单项。
- 记录写入和菜单完成必须同事务成功或回滚。
- 同一记录最多三张照片，排序不能重复。
- 菜谱永久删除与菜单项删除只解除关联，历史保留。

### 13.2 应用逻辑

- 完成输入验证覆盖空白备注、份数边界、评分边界、照片数量和 UUID。
- 照片路径只能位于当前用户与当前记录的固定前缀下。
- 上传失败和数据库失败都会保留本地烹饪会话。
- 数据库失败后只清理本次新上传的安全路径。
- 最近记录按 `completed_at desc, id desc` 稳定排序。
- 平均评分忽略未评分记录，“下次注意”使用最新非空备注。

### 13.3 组件与页面

- 最后一步点击完成后打开复盘面板，而不是立即清理会话。
- 不填写可选字段也能保存。
- 可上传、预览和移除最多三张图片。
- 直接从菜谱进入时不关联菜单；从周菜单进入时正确预填份数并完成菜单项。
- 菜谱详情正确显示空状态、统计、最近三次记录、照片和最新改进备注。
- 手机和桌面布局、键盘操作、ARIA 标签与错误状态通过测试。

### 13.4 回归与发布门禁

- 运行 cooking-history、cooking、meal-plans、recipes、media 和数据库相关测试。
- 运行完整 TypeScript 检查、ESLint、Vitest 和 Production build。
- 检查 git diff、敏感信息和未跟踪临时文件。
- 迁移执行到 Supabase 前再次确认项目 ref 和 SQL 文件。
- Preview 验收通过后暂停；Production 发布需要单独明确确认。

## 14. 人工验收场景

1. 从普通菜谱开始烹饪，不填写评分、照片和备注也能完成并留下记录。
2. 再做一次同一道菜，填写 5 星、两张照片和“下次少放盐”，详情显示两次记录与正确平均分。
3. 从周菜单的四人份菜谱进入，复盘默认四人份，保存后菜单项变为已完成。
4. 篡改 `mealPlanEntryId` 为其他用户或其他菜谱的菜单项，不能产生关联或修改菜单。
5. 模拟照片上传失败，表单和烹饪进度仍然存在，可移除照片后完成。
6. 模拟数据库失败，菜单项不变、记录不存在、本地会话不被清除。
7. 永久删除测试菜谱，历史记录仍保留菜名快照；删除菜单项后历史只解除菜单关联。
8. 刷新菜谱详情，统计、最近记录和私有签名照片正确显示。
9. 使用另一个用户登录，不能看到或操作前一个用户的烹饪历史。

## 15. 交付边界

模块 9 作为一个独立模块完成数据库、完成复盘、成品照片、周菜单联动和菜谱详情记录展示。实现完成后必须运行完整质量门禁，提交并推送 `feat/recipe-app-shopping`，然后暂停等待用户验收。
