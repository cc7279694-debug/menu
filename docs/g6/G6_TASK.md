## 二、G6 产品目标

G6 的目标不是生成新菜谱，而是让用户在已有菜谱的基础上，根据本次实际做菜人数，安全、直观地查看相应食材用量。

典型流程：

1. 用户打开原本为 3 人份的可乐鸡翅菜谱。
2. 将本次人数调整为 2 人。
3. 原来 600 克的鸡翅显示为 400 克。
4. 原来 330 毫升的可乐显示为 220 毫升。
5. “盐适量”“少许”等不能可靠计算的用量保留原文。
6. 用户进入 Focus / Guided 厨房模式，在食材参考面板中看到同一份调整结果。
7. 退出后原始菜谱、食材、步骤、历史记录及备份均不改变。

这是**规则式的本地比例计算，不是 AI 推断**。不得调用真实 AI 或将食材数据发送到网络。

## 三、G6-A：份量计算核心

### 3.1 使用既有模型

已知当前源码：

- `src/native/recipe-model.ts` 中 `servings` 为可空数字。
- `ingredients[].amount` 是自由文本，不是规范化的数字和单位。
- 现有 `RecipeDetails`、`RecipeLibrary` 可以保持原样。
- `preview-store.ts` 已有历史数据映射，不需要更改。

优先建立独立纯函数模块，例如：

`src/native/serving-adjustment.ts`

并配套单元测试。

严格区分：

- `originalServings`：菜谱真实读取到的原始份数。
- `targetServings`：本次临时选择的份数。
- `ratio`：仅用于显示的计算比例。
- `originalAmount`：数据库中保存的食材原文。
- `displayAmount`：临时计算后的展示值。

不得修改或重用数据持久化对象来保存 `displayAmount`。

尤其注意现有 legacy 映射中的 `baseServings` 与 `referenceServings`：应遵守已有 `RecipeDetails.servings` 的真实语义，不能把底层某个兼容默认值擅自当作用户填写的份数。

### 3.2 计算规则

计算公式：

`显示用量 = 原始用量 × 目标份数 ÷ 原始份数`

仅在原始份数与目标份数均为有效、有限、正数时计算。

目标份数必须在现有 Schema 允许的 `0.1～10000` 范围内，不得因 UI 控件新增限制而使既有合法菜谱无法正常显示。可以提供快捷加减按钮和直接输入，按钮步长采用便于操作的数值，输入仍应兼容合法的小数份数。

不合法、为空、输入过程中的临时无效值不能引发 NaN、Infinity、崩溃或写入。界面应显示可理解的校验信息，并保留最近一次有效展示值或安全回退到原文。

### 3.3 保守解析策略

第一版只支持**整个用量字段具有单一、明确数字和单位**的情况。

优先支持：

- 克、g、千克、公斤、kg
- 毫升、ml、mL、升、L
- 个、只、颗、片、根、瓣

允许正常空格、合法小数、半角及全角数字。只规范化计算过程，不改写原始数据。

暂不为了增加覆盖率而猜测复杂语言的含义。

以下用量应保持原文：

- `适量`
- `少许`
- `半勺`
- `一把`
- `1～2 勺`
- `1/2 茶匙`
- `1袋（约200克）`
- `2勺加少许`
- 缺失单位、多个数量混在一起或无法确定语义的文本

不能扫描食材名称中的数字并推断为用量；不能把自由文本中的数字片段单独抽出强行计算。

### 3.4 精度与可读性

计算后最多显示两位小数，去除不必要的末尾零，不使用科学计数法。

若发生四舍五入或离散计数单位得到小数，显示“约”以避免虚假精确感。

必须保证：

- 不把有效的极小正数静默舍入成 0。
- 不出现负值、NaN、Infinity 或异常超大结果。
- 极端值无法安全表示时，回退原始用量。
- 比例等于 1 时直接显示原始文本，不重新格式化。
- 不自动把克转换为千克或将毫升转换为升。
- 不推算烹饪时间、温度、热量、调味强度或步骤内容。

至少覆盖以下测试：

| 原始份数 → 目标份数 | 原用量 | 期望 |
|---|---|---|
| 3 → 2 | 600 克 | 400 克 |
| 3 → 2 | 330 毫升 | 220 毫升 |
| 3 → 2 | 3 个 | 2 个 |
| 3 → 2 | 2 个 | 约 1.33 个 |
| 3 → 3 | 1.50 kg | 原样显示 1.50 kg |
| 3 → 2 | 盐适量 | 原文不变 |
| 3 → 2 | 1～2 勺 | 原文不变 |
| null → 2 | 600 克 | 不换算，提示缺少原始份数 |

也应测试负数、0、极端值、小数、异常文本、全角数字、空用量、长文本、数值溢出及原始对象不可变性。

## 四、G6-B：菜谱详情交互

修改以现有实现为主：

- `src/native/recipe-detail.tsx`
- `src/native/library-app.tsx`
- `src/native/ui-v2/components.tsx`

可新增小型可复用的份量控制组件及专属 G6 CSS。

### 4.1 详情页体验

在现有菜谱详情的份量和食材区域内加入简洁控制。

展示：

- 原始份数。
- 本次目标份数。
- 加、减或直接输入操作。
- 恢复原始份数。
- 明确说明“仅调整本次查看，不修改原菜谱”。

调整后食材立即更新，不必重新加载页面。

用户应该能够理解自己看到的是临时用量，而不是已经编辑保存的菜谱。

如果原始份数缺失：

- 不假设默认 1 人份。
- 不提供虚假的换算结果。
- 保留原始食材信息。
- 给出简短提示：需要先在菜谱编辑中填写原始份数。

如果某些用量无法换算，保留原文；允许简短说明部分食材需要自行判断，不将其显示成计算成功。

### 4.2 状态生命周期

临时份量状态的所有权应放在既有页面/会话层，由详情页和厨房模式共同使用。

要求：

- 进入菜谱时默认原始份数。
- 详情 → 厨房 → 详情期间保持当前目标份数。
- 厨房里改变目标份数，详情也应同步。
- 打开另一道菜必须重新初始化。
- 离开菜谱后重新进入，应恢复其原始份数。
- 原菜谱被编辑并成功保存后，应基于最新内容重置换算。
- 应用重启后不得从持久存储恢复 G6 临时份量。

不要写入 SQLite、IndexedDB、localStorage、SessionStorage、DataStore、Backup、历史记录或其他持久存储。

不要改变既有编辑草稿、取消和保存语义。

## 六、G6-D：视觉、可用性和遗留文案

### 6.1 设计约束

继续 Glass Minimal。

三主题保持既有色彩、卡片、排版、按钮和导航风格，不重做全局 UI，不更换 Logo。

界面应适合厨房单手使用：

- 主操作容易识别和点击。
- 加减按钮至少满足既有触控尺寸要求。
- 数字与单位清晰。
- 原始与调整后的用量容易区分。
- 不造成横向溢出。
- 长菜名、长食材名、长单位文本能正常换行。
- 320 / 390 / 412px 宽度和浏览器 200% 字号下仍可操作。
- 不遮挡既有底部“开始烹饪”“下一步”等主要按钮。
- 兼容三主题、纯色回退和 reduced-motion。

新增样式应按 G5 的 scoped CSS 模式管理，不全局污染既有组件。

### 6.2 无障碍

- 人数输入具有准确标签，例如“本次做几人份”。
- 加减按钮具备准确的无障碍名称。
- 当前人数变化有适当的状态反馈，避免重复播报大量食材。
- 错误信息应关联输入。
- 键盘、焦点、Sheet 打开关闭及返回行为保持正确。
- 不仅依赖颜色区分“原始用量”和“调整用量”。

### 6.3 顺便修正 G5 已记录的小问题

G5 的“较早的 N 次记录”实际只统计详情页显示的较早预览记录，容易让人误以为全部历史仅有 N 次。

本轮可以做最小文案修正，例如：

`展开较早记录（预览 N 条）`

实际完整记录继续由原有“查看做菜记录”入口访问。

只修改展示文案，不修改历史查询数量、排序或数据逻辑。其余 G5 NOTES 不扩大为单独重构。
